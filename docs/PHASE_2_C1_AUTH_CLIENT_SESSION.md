# Phase 2-C1: Auth Client & Session Contract

## الحالة

- وثيقة عقد وتصميم للتنفيذ القادم.
- لا تحتوي تنفيذًا إنتاجيًا أو واجهة دخول أو Migration.
- تعتمد على قرارات Phase 2-C0.
- حالة المرحلة: قادمة، ولا تُعلن مكتملة قبل الكود والاختبارات.

## 1. الهدف

إنشاء طبقة Auth موحدة وكسولة فوق عميل Supabase الحالي، توفر عقدًا واضحًا للمصادقة والجلسة والتسجيل وتغيّر حالة Auth، دون خلطها بالتفويض أو Profile.

## 2. حدود C1

داخل C1:

- أنواع Auth التطبيقية.
- خدمة Auth.
- استعادة الجلسة الحالية.
- تسجيل الدخول بالبريد وكلمة المرور.
- التسجيل.
- تسجيل الخروج.
- الاشتراك في تغيّر حالة Auth.
- تحويل الأخطاء إلى رسائل عامة آمنة.
- اختبارات وحدة مع عميل وهمي.

خارج C1:

- `profiles` وTrigger.
- Roles وAuthorization RLS.
- شاشة الدخول والتسجيل.
- Guards الواجهة.
- `mastery_results`.
- أي كتابة بيانات تعليمية.

## 3. استخدام عميل Supabase الحالي

لا يُنشأ عميل Supabase ثانٍ.

تستخدم خدمة Auth العميل الكسول الموجود في طبقة البيانات، مع الحفاظ على القواعد التالية:

- مجرد استيراد ملفات Auth لا يهيئ Supabase.
- لا تُقرأ متغيرات البيئة قبل أول استخدام فعلي.
- لا يُستخدم `service_role` أو Secret في كود العميل.
- لا يُنشأ أكثر من عميل بسبب إعادة التصيير.

## 4. فصل AuthState عن AuthorizationState

C1 تعرف حالة Supabase Auth فقط.

وجود جلسة يعني:

> هوية المستخدم معروفة والجلسة صالحة.

ولا يعني:

- أن Profile موجود.
- أن الحساب `active`.
- أن الحساب غير معلّق.
- أن الدور طالب أو معلم أو مراجع.
- أن المستخدم مخوّل لواجهة أو عملية محمية.

فحص `profiles.role` و`profiles.status` يبدأ في Phase 2-C2 ضمن طبقة Authorization أعلى.

## 5. AuthState

العقد المبدئي:

```ts
type AuthState =
  | { status: 'loading' }
  | { status: 'guest' }
  | {
      status: 'authenticated';
      user: AuthUser;
      session: AuthSession;
    }
  | {
      status: 'error';
      error: PublicAuthError;
    };
```

لا تُسمى الحالة `authorized` لمجرد وجود جلسة.

لا يُسمح بحالة مبهمة يكون فيها المستخدم موجودًا والجلسة غير معروفة.

## 6. AuthorizationState المستقبلية

تُضاف في C2 طبقة مستقلة، مثل:

```ts
type AuthorizationState =
  | { status: 'loading_profile'; user: AuthUser; session: AuthSession }
  | { status: 'authorized'; user: AuthUser; session: AuthSession; profile: UserProfile }
  | { status: 'pending'; user: AuthUser; session: AuthSession; profile: UserProfile }
  | { status: 'suspended'; user: AuthUser; session: AuthSession; profile: UserProfile }
  | {
      status: 'profile_error';
      user: AuthUser;
      session: AuthSession;
      error: PublicAuthorizationError;
    };
```

C1 تجيب: هل المستخدم مسجل الدخول؟

C2 تجيب: هل الحساب مسموح له، وما دوره؟

## 7. عقد الخدمة

التصور الأولي لدوال الخدمة:

```ts
getCurrentSession()
getCurrentUser()
signInWithPassword()
signUp()
signOut()
onAuthStateChange()
```

يجب أن تكون الأنواع التطبيقية مستقلة عن أشكال Supabase الخام قدر الإمكان، مع الاحتفاظ بالحد الأدنى اللازم من معرف المستخدم والجلسة.

## 8. استعادة الجلسة

عند أول استخدام فعلي للتطبيق:

1. تبدأ الحالة `loading`.
2. تُقرأ الجلسة الحالية مرة واحدة.
3. إن لم توجد جلسة تصبح الحالة `guest`.
4. إن وجدت جلسة صالحة تصبح `authenticated`.
5. إن فشل الطلب بخطأ حقيقي تصبح `error` برسالة عامة.

لا تُعرض واجهة محمية قبل اكتمال هذه الخطوة.

## 9. الاشتراك في تغيّر Auth

- يوجد اشتراك مركزي واحد في تغيّر حالة Auth.
- يعيد العقد دالة إلغاء اشتراك واضحة.
- يجب إلغاء الاشتراك عند التخلص من المستهلك.
- لا تُنشأ مستمعات متعددة بسبب إعادة التصيير.
- لا تُنفذ عمليات async ثقيلة مباشرة داخل callback بما قد يعطل تدفق Supabase Auth.
- تغيّر Auth لا يحسم Authorization؛ تحميل Profile يأتي في C2.

## 10. Confirm Email

الإعداد الرسمي المعتمد للمشروع:

```text
Confirm email = Enabled
```

وعليه، قد تعيد `signUp()`:

- مستخدمًا مع `session: null` حتى تأكيد البريد.
- مستخدمًا وجلسة فعالة في بيئة مختلفة أو إذا تغير الإعداد لاحقًا.

يجب أن يدعم العقد المسارين دفاعيًا، دون افتراض أن التسجيل يعيد جلسة دائمًا.

## 11. SignUpResult

يحتوي العقد **ثلاث حالات كاملة**:

```ts
type SignUpResult =
  | {
      status: 'confirmation_required';
      email: string;
    }
  | {
      status: 'authenticated';
      user: AuthUser;
      session: AuthSession;
    }
  | {
      status: 'error';
      error: PublicAuthError;
    };
```

التفسير:

- `confirmation_required`: التسجيل لم يُنشئ جلسة، وتُعرض رسالة التأكيد المحايدة.
- `authenticated`: توجد جلسة مباشرة، ويُدعم هذا المسار دفاعيًا.
- `error`: خطأ حقيقي قابل للتصنيف والعرض الآمن، مثل إدخال غير صالح أو كلمة مرور ضعيفة أو معدل محاولات مرتفع أو فشل شبكة.

لا ترفض خدمة التسجيل الوعد لأخطاء Auth المتوقعة؛ تحوّلها إلى حالة `error` موحدة. الاستثناءات غير المتوقعة تُلتقط وتُحوّل كذلك إلى `PublicAuthError` مع حفظ السبب داخليًا.

## 12. منع تعداد البريد الإلكتروني

لا تحاول الواجهة أو الخدمة تحديد ما إذا كان البريد مسجلاً مسبقًا.

عند تفعيل Confirm Email قد تستخدم Supabase استجابة معتمة تمنع كشف وجود الحساب.

لا يوجد كود عام مثل:

```text
email_already_exists
```

ولا تظهر رسالة:

```text
البريد مستخدم مسبقًا
```

الرسالة المعتمدة دائمًا عند `confirmation_required`:

> إذا كان البريد صالحًا لإكمال التسجيل، فستصلك رسالة تأكيد. تحقّق من صندوق الوارد والرسائل غير المرغوب فيها.

لا تقول الواجهة قطعًا: «تم إنشاء حسابك».

## 13. PublicAuthError

التصور المبدئي:

```ts
type PublicAuthErrorCode =
  | 'invalid_input'
  | 'invalid_credentials'
  | 'weak_password'
  | 'rate_limited'
  | 'network_error'
  | 'service_unavailable'
  | 'unknown';

interface PublicAuthError {
  code: PublicAuthErrorCode;
  message: string;
}
```

الخطأ العام لا يحتوي:

- Stack trace.
- تفاصيل SMTP.
- أسماء جداول أو Triggers.
- رسالة Supabase الخام كاملة.
- معلومة تثبت وجود البريد.

## 14. رسائل الأخطاء

يجوز عرض رسائل مفيدة وآمنة لأخطاء لا تكشف وجود حساب، مثل:

- أدخل بريدًا إلكترونيًا صالحًا.
- كلمة المرور لا تحقق متطلبات الأمان.
- بيانات الدخول غير صحيحة.
- تم إجراء محاولات كثيرة. حاول لاحقًا.
- تعذر الاتصال بالخدمة حاليًا.

لا تعتمد الواجهة على النص الخام لـ`error.message` لاتخاذ قرار منطقي؛ تعتمد على `code` التطبيقية.

## 15. تسجيل الدخول

`signInWithPassword()`:

- يعيد نجاحًا يتضمن المستخدم والجلسة عند نجاح Auth.
- يعيد `PublicAuthError` عند خطأ متوقع.
- لا يكشف إن كان البريد موجودًا؛ رسالة بيانات الدخول تبقى عامة.
- لا يعتبر المستخدم مخولاً حتى اكتمال Profile في C2.

يُحسم شكل `SignInResult` النهائي أثناء تنفيذ C1، مع الحفاظ على نفس مبادئ `SignUpResult` والأخطاء العامة.

## 16. تسجيل الخروج

`signOut()`:

- يطلب إنهاء الجلسة من Supabase.
- يحول النجاح إلى حالة `guest` على مستوى Auth.
- يحول الخطأ المتوقع إلى `PublicAuthError`.
- لا يمسح بيانات تعليمية محلية أو سحابية خارج نطاقه.
- تنظيف أي cache مرتبط بالهوية يُحدّد صراحة عند ربط C2/C3، لا يُنفذ ضمن C1 بلا عقد.

## 17. AbortSignal والإلغاء

يُستخدم `AbortSignal` فقط في العمليات التي تدعم تمريره فعليًا في Supabase Auth أو في طبقة الشبكة المعتمدة.

لا تُضاف معلمة شكلية توحي بإلغاء غير حقيقي.

إذا وصل `AbortError` فعلي:

- يُحافظ على دلالته.
- لا يتحول إلى رسالة «بيانات الدخول غير صحيحة».
- لا يُسجل كخطأ مستخدم عادي.

تفاصيل دعم الإلغاء لكل دالة تُثبت من واجهة Supabase الفعلية قبل التنفيذ.

## 18. معالجة الأخطاء الداخلية

- أخطاء Supabase الخام تُحوّل داخل خدمة Auth.
- تُحفظ العلة الأصلية داخليًا في `cause` عند إنشاء خطأ تقني مغلف.
- لا تُعرض `cause` للواجهة.
- الأخطاء المتوقعة تعود كعقود نتيجة واضحة.
- الأخطاء غير المتوقعة لا تتسرب بنصها الخام.

## 19. التهيئة الكسولة

معايير التهيئة:

- استيراد ملف Auth لا يقرأ البيئة.
- استيراد ملف Auth لا ينشئ عميل Supabase.
- العميل يُطلب عند أول عملية Auth فعلية فقط.
- تكرار الاستدعاء يستخدم نفس العميل والمستمع المركزي وفق العقد.

## 20. اختبارات C1 المطلوبة

- الاستيراد المجرد لا يهيئ Supabase.
- استعادة جلسة موجودة.
- غياب الجلسة يعيد `guest`.
- تسجيل دخول ناجح.
- بيانات دخول مرفوضة برسالة عامة.
- تسجيل `confirmation_required` مع `session: null`.
- تسجيل `authenticated` مع جلسة.
- تسجيل يفشل بكلمة مرور ضعيفة.
- تسجيل يفشل بسبب rate limiting.
- عدم كشف وجود البريد.
- تسجيل خروج ناجح.
- تسجيل خروج فاشل برسالة عامة.
- الاشتراك في تغير Auth.
- إلغاء الاشتراك.
- عدم إنشاء مستمعات متعددة.
- عدم اعتبار الجلسة تفويضًا كاملاً.
- الحفاظ على `AbortError` حيث يكون الإلغاء مدعومًا فعليًا.
- تغليف الأخطاء الداخلية مع `cause` دون كشفه للواجهة.

## 21. معايير قبول Phase 2-C1 التوثيقية

تُعد وثيقة C1 معتمدة عند تثبيت ما يلي:

- استخدام عميل Supabase الحالي بتهيئة كسولة.
- فصل `AuthState` عن `AuthorizationState`.
- اعتماد Confirm Email مفعلاً.
- دعم `session: null` كنتيجة طبيعية للتسجيل.
- وجود `SignUpResult` بالحالات الثلاث: `confirmation_required / authenticated / error`.
- اعتماد رسالة تسجيل محايدة تمنع تعداد البريد.
- تحويل الأخطاء الخام إلى `PublicAuthError`.
- عدم كشف وجود البريد أو تفاصيل Supabase الداخلية.
- اشتراك مركزي قابل للإلغاء في تغيّر Auth.
- عدم ادعاء دعم AbortSignal إلا حيث تدعمه الواجهة الفعلية.
- إبقاء Profiles وRLS وواجهات Auth خارج تنفيذ C1.
- إبقاء `mastery_results` في Phase 2-D.
