# Phase 3 — Mobile Visual Acceptance Contract

## الهدف

هذه بوابة قبول بصرية بشرية إلزامية قبل `v0.6-teacher-dashboard-complete`.

الاختبارات الآلية تثبت المنطق والعقود، لكنها لا تستطيع وحدها إثبات أن واجهة RTL العربية قابلة للاستخدام على شاشة هاتف دون قص أو تراكب أو تمرير أفقي غير مقصود.

## بيئة القبول

يُنفذ القبول على الالتزام نفسه الذي نجح عليه:

```text
npm run verify:phase-3-closure
```

تُستخدم Supabase المحلية فقط. لا يلزم نشر Remote Supabase لهذا القبول.

افحص أحجام العرض التالية عند تكبير المتصفح 100%:

```text
360 x 800   هاتف ضيق — بوابة الحد الأدنى
390 x 844   هاتف شائع — بوابة الهاتف الأساسية
768 x 1024  جهاز لوحي عمودي — بوابة الانتقال
```

يمكن استخدام Chrome/Edge Device Mode أو جهاز فعلي. الحكم بصري وتفاعلي، لا مجرد لقطة شاشة ساكنة.

## قواعد PASS العامة

في كل شاشة إلزامية يجب تحقق جميع الآتي:

- لا يوجد horizontal viewport scroll على مستوى الصفحة.
- لا يُقص عنوان أو نص أو زر أو حقل إدخال خارج الشاشة.
- RTL منطقي: بداية النص والحقول والأزرار الأساسية متسقة مع العربية.
- العناصر المتجاورة تتحول إلى stacking مناسب عند ضيق العرض بدل التصادم.
- الأزرار قابلة للنقر ولا تتراكب ولا تختفي خلف عناصر ثابتة.
- النص العربي الطويل يلتف ولا يوسّع الحاوية خارج viewport.
- رسائل الخطأ والحالة وSubmission Readiness مقروءة كاملة.
- الحقول والقوائم لا تتجاوز عرض الحاوية.
- لا تختفي عناصر التحكم الأساسية بعد فتح محرر فرعي أو حالة Validation.
- لا توجد مساحة فارغة شاذة سببها تخطيط سطح المكتب بعد التحول للهاتف.
- لا تعتمد مهمة أساسية على hover فقط.
- لا يتغير معنى الإجراء عند الانتقال بين الهاتف واللوحي.

## مسار المعلم الإلزامي

افحص بحساب `teacher` نشط:

1. Teacher Workspace وقائمة المسودات.
2. إنشاء درس جديد وحقول بيانات الدرس.
3. فتح مسودة قائمة.
4. محرر الأهداف:
   - إضافة هدف.
   - تعديل هدف.
   - حذف هدف في حالة مسموحة.
5. محرر الأسئلة:
   - فتح Question Buffer.
   - كتابة السؤال.
   - التعامل مع الاختيارات عند السؤال متعدد الخيارات.
   - اختيار/تغيير الهدف المرتبط.
   - حالة mastery عند وجودها.
   - تطبيق السؤال والعودة للمحرر.
6. Submission Readiness:
   - حالة غير جاهزة.
   - حالة جاهزة بعد اكتمال المحتوى.
7. شريط/منطقة الإجراءات:
   - حفظ المسودة.
   - الإرسال للمراجعة عندما تكون الشروط مكتملة.

الحكم لا يتطلب نشر محتوى بعيدًا؛ المطلوب قابلية الاستخدام الفعلية على Supabase المحلية.

## مسار المراجع الإلزامي

افحص بحساب `reviewer` نشط:

1. Reviewer Workspace.
2. قائمة المراجعات المعلقة.
3. فتح Revision للمراجعة.
4. قراءة بيانات الدرس والأهداف والأسئلة دون قص أفقي.
5. منطقة قرار المراجعة.
6. حقل سبب الرفض عندما يكون مطلوبًا.
7. أزرار الرفض والاعتماد وحالات disabled/loading/error.

## حالات الضغط البصري

اختبر على الأقل:

- عنوان درس عربي طويل نسبيًا.
- هدف تعليمي طويل يلتف إلى أكثر من سطر.
- نص سؤال طويل.
- خيار إجابة طويل.
- رسالة خطأ أو تنبيه أطول من سطر.
- وجود أكثر من بطاقة/مسودة في القائمة.

لا تحتاج إلى اختراع بيانات غير منطقية؛ المطلوب فقط التأكد أن التخطيط يتحمل نصوصًا عربية واقعية بدل أن ينجح مع كلمتين ثم ينهار أمام جملة، وهو إنجاز شائع جدًا في واجهات البشر للأسف.

## قاعدة الإغلاق

`OVERALL: PASS` شرط سابق للوسم.

إذا ظهر `FAIL`:

1. لا تنشئ `v0.6-teacher-dashboard-complete`.
2. أصلح العيب في دفعة محددة.
3. أعد الاختبارات الآلية المتأثرة.
4. أعد `npm run verify:phase-3-closure` على الالتزام الجديد.
5. أعد Mobile Visual Acceptance كاملًا على الالتزام الجديد.

لا يُنقل PASS من commit قديم إلى commit جديد.
