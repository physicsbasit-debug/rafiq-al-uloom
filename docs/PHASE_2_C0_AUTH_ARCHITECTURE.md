# Phase 2-C0: Authentication & Authorization Architecture

## الحالة

- وثيقة قرارات معمارية وأمنية معتمدة.
- لا تحتوي كودًا إنتاجيًا أو Migration أو تنفيذًا فعليًا.
- تعتمد على نقطة الاستقرار `v0.3-data-layer-complete`.
- تمهّد لتنفيذ Phase 2-C1 إلى Phase 2-C5.

## 1. الهدف

إضافة طبقة هوية وصلاحيات إلى «رفيق العلوم» دون كسر طبقة المحتوى أو التكافؤ المثبت بين المزوّد المحلي وSupabase.

تشمل Phase 2-C:

- الهوية والمصادقة.
- الجلسات واستعادتها.
- الأدوار التطبيقية وحالات الحساب.
- حماية العمليات والبيانات.
- سياسات RLS المرتبطة بالهوية والتفويض.
- تجهيز الأساس الذي ستعتمد عليه Cloud Persistence في Phase 2-D.

لا تشمل Phase 2-C:

- حفظ `mastery_results`.
- مزامنة تقدم الطالب بين الأجهزة.
- لوحة المعلم الكاملة.
- التأليف بالذكاء الاصطناعي.

## 2. مزوّد الهوية

المزوّد الرسمي المعتمد هو **Supabase Auth**.

أسباب الاختيار:

- التكامل المباشر مع PostgreSQL وRLS.
- توفير `auth.uid()` و`auth.role()` والجلسات وJWT دون جسر هوية إضافي.
- التوافق مع أدوار PostgreSQL الحالية: `anon` و`authenticated` و`service_role`.
- استخدام البنية الموجودة بدل إدخال Firebase أو Auth0 أو Clerk أو JWT مخصّص بلا حاجة عملية.

## 3. الفصل بين المصادقة والتفويض

دور PostgreSQL `authenticated` يعني فقط أن هوية المستخدم تم التحقق منها.

لا يعني ذلك أن المستخدم:

- طالب.
- معلم.
- مراجع.
- نشط أو غير معلّق.
- مخوّل لعملية محمية.

الأدوار التطبيقية وحالة الحساب تُقرأ من `public.profiles`، لا من مجرد وجود جلسة.

## 4. مصدر التفويض التطبيقي

يعتمد المشروع جدولًا مستقلاً:

```text
public.profiles
```

التصور الأولي:

```text
id            uuid → auth.users.id
display_name  text
role          student | teacher | reviewer
status        pending | active | suspended
created_at    timestamptz
updated_at    timestamptz
```

يرتبط `profiles.id` بـ`auth.users.id` مع `ON DELETE CASCADE`.

## 5. منع استخدام بيانات المستخدم القابلة للتعديل للتفويض

لا تُخزّن الأدوار أو حالات الحساب الأمنية داخل:

- `user_metadata`
- `raw_user_meta_data`
- أي حقل يستطيع العميل تعديله مباشرة

السبب: التفويض لا يجوز أن يعتمد على بيانات يمكن للمستخدم تغييرها بنفسه.

## 6. حماية `profiles` من التعديل الذاتي

الحقول الأمنية المحمية هي:

```text
role
status
```

يُسمح للمستخدم المصادق عليه بقراءة ملفه الشخصي فقط، وبقراءة الحقول اللازمة لعرض اسمه ودوره وحالة حسابه.

لا يُسمح له عبر أي مسار عميل عام بـ:

- تعديل `role`.
- تعديل `status`.
- ترقية نفسه إلى `teacher` أو `reviewer`.
- إعادة تفعيل حساب `suspended`.
- تعديل صف مستخدم آخر.
- إنشاء Profile بديل.
- حذف Profile مباشرة.

يمكن لاحقًا السماح بتعديل حقول شخصية غير أمنية مثل `display_name` بسياسة مستقلة، دون فتح تعديل `role` أو `status`.

تغيير `role` و`status` يتم حصريًا عبر مسار إداري خلفي موثوق يُصمّم في Phase 2-C2، مثل دالة PostgreSQL محمية أو Edge Function موثوقة أو عملية إدارية خارج كود العميل.

القاعدة الملزمة:

> المستخدم لا يملك سلطة تعديل صفته الأمنية.

إخفاء الحقول أو الأزرار في React ليس حماية أمنية؛ الحماية الفعلية تكون عبر RLS والقيود ومسار إداري خلفي واختبارات صلاحيات حقيقية.

## 7. الأدوار التطبيقية

الأدوار الأولية المعتمدة:

- `student`
- `teacher`
- `reviewer`

لا تُضاف أدوار أخرى في Phase 2-C دون قرار مكتوب وتحديث الوثيقة.

## 8. حالات الحساب

الحالات المعتمدة:

- `pending`
- `active`
- `suspended`

### pending

حساب موجود لكنه لم يحصل بعد على الوصول المحمي الكامل. تفاصيل التفعيل والمسار الإداري تُحسم في Phase 2-C2.

### active

يستخدم النظام بحسب دوره وسياسات التفويض.

### suspended

الحظر كامل، ولا يوجد وضع وصول محدود في Phase 2-C.

يُمنع الحساب المعلّق من:

- الوصول للمحتوى المحمي.
- قراءة المسودات.
- الكتابة أو المراجعة أو الاعتماد.
- الوصول المستقبلي إلى `mastery_results`.
- تنفيذ أي عملية محمية.

تظهر رسالة عامة:

> هذا الحساب غير متاح حاليًا. تواصل مع إدارة النظام.

لا تُعرض تفاصيل التعليق الإدارية للعميل.

## 9. وضع الزائر وAnonymous Sign-In

لا يُفعّل Supabase Anonymous Sign-In في Phase 2-C.

يبقى وضع الزائر الحالي مسارًا محليًا مستقلاً:

- بلا حساب.
- بلا جلسة Auth.
- بلا صف `profiles`.
- بلا حفظ سحابي.
- بلا مزامنة بين الأجهزة.
- بلا صلاحيات معلم أو مراجع.
- يستخدم المزوّد المحلي.

Cloud Persistence تتطلب حسابًا دائمًا مسجلاً.

## 10. إنشاء Profile تلقائيًا

يُنشأ صف `public.profiles` تلقائيًا عند إنشاء مستخدم في `auth.users` عبر Trigger داخل Migration جديدة في Phase 2-C2.

يجب أن يكون الـTrigger:

- بسيطًا ومحدود المسؤولية.
- قابلاً للاختبار بعد `npx supabase db reset`.
- غير معتمد على كائنات غير موجودة وقت التنفيذ.
- موثق الفشل بوضوح.

## 11. ذرّية التسجيل وفشل Trigger

إنشاء المستخدم وProfile عملية ذرية واحدة.

إذا فشل Trigger إنشاء `public.profiles`:

- تفشل عملية التسجيل كاملة.
- تتراجع المعاملة.
- لا يبقى مستخدم في `auth.users` بلا Profile مطابق.
- لا توجد إعادة محاولة صامتة من العميل.
- لا يُسمح بالدخول المؤقت بلا Profile.

القاعدة الملزمة:

> لا يوجد مستخدم تطبيقي صالح بلا صف `public.profiles` مطابق.

في Phase 2-C2 يجب اختبار حالات فشل مصطنعة للـTrigger، والتأكد أن الاستعلام التالي يعيد صفر صفوف دائمًا:

```sql
SELECT au.id
FROM auth.users au
LEFT JOIN public.profiles p ON p.id = au.id
WHERE p.id IS NULL;
```

## 12. أثر الهوية على RLS

السياسات الحالية تجعل `anon` و`authenticated` متطابقين تقريبًا في قراءة المحتوى المعتمد.

تعديل RLS يدخل رسميًا في **Phase 2-C2** عبر Migration جديدة، دون تعديل Migrations المطبقة.

السياسات الجديدة تستند إلى:

```text
auth.uid()
→ profiles.id
→ profiles.role
→ profiles.status
```

ولا يكفي `auth.role() = 'authenticated'` لإثبات التفويض التطبيقي.

## 13. اتجاه الوصول المبدئي

| الحالة | الوصول المتوقع |
| --- | --- |
| زائر محلي | المحتوى العام عبر الوضع المحلي |
| طالب `active` | المحتوى المعتمد |
| معلم `active` | المحتوى المعتمد والمسودات المسموح بها وفق الملكية |
| مراجع `active` | المحتوى المسند أو المسموح له بمراجعته |
| `pending` | لا وصول محمي كامل حتى التفعيل |
| `suspended` | حظر كامل |

تفاصيل ملكية المسودات وإسناد المراجعة وتغيير `draft → approved` تُحسم في Phase 2-C2 قبل كتابة سياسات المحتوى.

## 14. الجلسة لا تساوي صلاحية

الجلسة تثبت الهوية فقط.

بعد وجود جلسة يجب تحميل Profile والتحقق من:

- وجود Profile.
- `status`.
- `role`.

لا تُعرض واجهة محمية لمجرد وجود JWT صالح.

## 15. الحماية متعددة الطبقات

الحماية تعتمد على:

- RLS كخط دفاع حقيقي للبيانات.
- Authorization Guards في التطبيق لمنع الارتباك والمسارات غير المسموحة.
- مسارات خلفية موثوقة للعمليات الإدارية.
- اختبارات وحدة وتكامل وصلاحيات فعلية.

إخفاء زر أو تبويب ليس بديلاً عن RLS.

## 16. العلاقة مع Phase 2-D

Phase 2-C توفر هوية مستقرة ومعرّفًا:

```text
user_id
```

أما الحفظ الفعلي لـ:

- `mastery_results`
- تقدم الطالب
- الإحصاءات
- المزامنة بين الأجهزة

فيبقى ضمن **Phase 2-D: Cloud Persistence** بعقد تخزين مستقل وسياسات RLS مستقلة.

## 17. تغير طبيعة المخاطرة

Phase 2-C هي أول مرحلة تغيّر تجربة المستخدم المرئية بعد أن كانت مراحل البيانات السابقة خلفية أساسًا.

المخاطر الجديدة تشمل:

- شاشة دخول وتسجيل.
- استعادة الجلسة.
- رسائل الرفض.
- انتهاء الجلسة.
- حماية واجهات وعمليات.

لذلك تشمل معايير القبول لاحقًا:

- عدم وميض واجهة محمية قبل اكتمال التحقق.
- رسائل عربية واضحة لا تكشف معلومات حساسة.
- RTL وإمكانية الوصول.
- عدم فقدان المسار بلا تفسير عند انتهاء الجلسة.
- عدم إظهار عمليات لا يمكن تنفيذها.

## 18. تقسيم Phase 2-C

```text
2-C0  Auth & Authorization Architecture
2-C1  Auth Client & Session Contract
2-C2  Profiles + Roles + Authorization RLS
2-C3  Login / Logout / Session UI
2-C4  Protected Operations + Access Guards
2-C5  Integration Tests + Security Closure
```

## 19. خارج نطاق C0 وC1

- إنشاء جدول `profiles` فعليًا.
- Trigger التسجيل.
- RLS الخاصة بالأدوار.
- شاشة الدخول.
- Guards الواجهة.
- حفظ `mastery_results`.
- لوحة المعلم.
- التأليف بالذكاء الاصطناعي.

## 20. معايير قبول Phase 2-C0

تُعد C0 مكتملة عند اعتماد ما يلي:

- Supabase Auth مزود الهوية الرسمي.
- الفصل بين Authentication وAuthorization.
- `public.profiles` المصدر الوحيد للأدوار التطبيقية وحالة الحساب.
- عدم استخدام بيانات Metadata القابلة لتعديل المستخدم للتفويض.
- منع المستخدم من تعديل `role` و`status` أو ترقية نفسه أو إعادة تفعيل حسابه.
- حصر تغيير `role` و`status` في مسار إداري خلفي موثوق يُصمّم في C2.
- اعتماد الأدوار `student / teacher / reviewer`.
- اعتماد الحالات `pending / active / suspended`.
- اعتماد الحظر الكامل لـ`suspended`.
- عدم استخدام Anonymous Sign-In والإبقاء على وضع الزائر المحلي.
- اعتماد التسجيل الذري وعدم السماح بمستخدم يتيم بلا Profile.
- إدخال RLS المبنية على Profile ضمن C2 عبر Migration جديدة.
- إبقاء `mastery_results` وCloud Persistence في Phase 2-D.
- توثيق أن حماية الواجهة وحدها غير كافية.
